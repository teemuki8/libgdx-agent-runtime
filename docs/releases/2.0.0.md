# 2.0.0

The second production-supported release is a narrowly scoped breaking major: the Java diagnostic
model moves to structured immutable failure evidence with validated diagnostic-limit minimums, and
protocol 2.0 is additive while protocols 1.0-1.13 keep their frozen schemas and remain supported.
This release also hardens capture, lifecycle, transport, and serialization bounds
reported by issues #40-#50.

## Published artifacts

All artifacts require Java 25 and use group `io.github.teemuki8`:

- `agent-runtime-core`
- `agent-runtime-libgdx`
- `agent-runtime-protocol`
- `agent-runtime-mcp`

`runtime-fixtures` is qualification code and is not published.

## Included contract

- Frozen protocol 1.0-1.13 plus additive protocol 2.0: an explicit `capability(version, command)`
  predicate enables every existing V1.13 command under 2.0 regardless of its zero minor, adds the
  `runtime_entity_history` command, and carries structured failure evidence in callback-bearing
  failure results. Protocols 1.0-1.13 keep their exact command, response, error, bound, JSON, and
  MCP shapes and their original negotiation path; callback-failure diagnostic values now use the
  bounded legacy envelope instead of raw application messages.
- Structured `ApplicationFailureEvidence` (bounded category, exception class, session-prefixed
  correlation ID, optional sanitized detail) replaces raw exception messages and stack traces in
  externally queryable failure evidence; protocol 1.x projections render only the 642-character
  `correlationId|category|exceptionClass` legacy envelope.
- Bounded entity history for removed entities, bounded open-frame event/decision/cause staging,
  pre-retention determinism budgets, atomic checkpoint replacement, capture-thread-confined
  dynamic entity sources, safe cross-thread lifecycle status, and complete callback-registry
  release on close.
- Bounded strict-UTF-8 stdio JSON-RPC framing and response serialization through hard byte caps,
  so neither oversized input nor oversized output can materialize unbounded buffers.

The stable compatibility and support rules are recorded in
[ADR 0011](../adr/0011-stable-1x-compatibility.md) and [SECURITY.md](../../SECURITY.md); the
behavioral contract is recorded in [design-contract.md](../design-contract.md).

## Issue impact

Every open issue #40-#50 is closed by this release.

### Bounds and robustness

- [#40](https://github.com/teemuki8/libgdx-agent-runtime/issues/40) — dynamic entity sources are
  now enumerated sequentially on the capture thread through `stream.sequential().iterator()` with
  a hard global bound: exactly the first `entitiesPerSnapshot` non-null observations are retained,
  and the next non-null observation only proves truncation before enumeration stops across all
  sources. Parallel application streams can no longer escape the capture thread, and infinite or
  very large sources can no longer hang capture.
- [#45](https://github.com/teemuki8/libgdx-agent-runtime/issues/45) — open-frame events, decisions,
  and explicit change causes are bounded at insertion: `emit` retains at most `retainedEvents`,
  `beginDecision` at most `decisionsPerFrame`, and the new `FrameStagingLimits.causesPerFrame`
  caps `causeNextChange` map entries. Dropped inputs are never read or copied, counters saturate,
  and truncation evidence reports observed/retained/limit.
- [#43](https://github.com/teemuki8/libgdx-agent-runtime/issues/43) — determinism evidence limits
  are enforced before retention instead of after allocation: entity/fact counts are accumulated
  incrementally, admission stops at the first item that would exceed
  `maximumEntitiesPerFrame`/`maximumFactsPerFrame`, and a frame is retained only when its exact
  canonical encoded byte size fits `maximumEncodedEvidenceBytes`. Overshoot is impossible, the
  specific `INCONCLUSIVE` reason is retained, and no later tick or scenario reset runs.
- [#46](https://github.com/teemuki8/libgdx-agent-runtime/issues/46) — checkpoint replacement is
  failure atomic: the new handle is created before eviction, installation and old-entry removal
  happen in one synchronized block, and only the evicted handle is disposed afterward. A failed
  replacement keeps every prior descriptor/handle listed and restorable.

### Lifecycle and concurrency

- [#42](https://github.com/teemuki8/libgdx-agent-runtime/issues/42) — `status()` is backed by a
  `volatile` field and reads safely from any thread without a monitor; capture-thread-only
  monotonic transitions are unchanged.
- [#41](https://github.com/teemuki8/libgdx-agent-runtime/issues/41) — closing the runtime releases
  every callback-bearing registry (scenario reset handlers, action handlers, simulation control
  callbacks and condition predicates, input handlers and queued/scheduled injections, checkpoint
  providers and opaque handles, pending command closures, pending operations) while immutable
  catalogs, completed history, and terminal evidence stay queryable. Every close hook runs, later
  failures are suppressed, `CLOSED` is always published, and repeated `close()` is a no-op.
- [#47](https://github.com/teemuki8/libgdx-agent-runtime/issues/47) — a throwing
  simulation-control stop condition now records `CALLBACK_FAILED` completion evidence (never
  `PENDING`) before the typed command failure propagates; completed-tick and frame evidence stays
  accurate and the original throwable still reaches sanitized command-failure classification.

### Security

- [#44](https://github.com/teemuki8/libgdx-agent-runtime/issues/44) — stdio JSON-RPC frames are
  bounded before parsing: a fixed `ProtocolJson.MAX_REQUEST_BYTES + 1` framer replaces
  `BufferedReader.readLine`, strict UTF-8 decoding (`CodingErrorAction.REPORT`) rejects malformed
  input, and the MCP mapper enforces the protocol codec's depth 32 / string 16,384 / number 128
  stream constraints on stdio. Oversized and malformed frames are drained, answered with one
  bounded null-id parse error, and do not terminate later valid requests.
- [#49](https://github.com/teemuki8/libgdx-agent-runtime/issues/49) — response byte limits are
  enforced during serialization instead of after: every response streams through a hard-cap sink
  so serialization aborts with `LIMIT_EXCEEDED` before byte `MAX_RESPONSE_BYTES + 1` is retained,
  and the MCP stdio transport serializes each actual `JSONRPCMessage` exactly once into a bounded
  buffer and writes those exact checked bytes. No unbounded intermediate array is ever
  materialized, and an oversized outbound message becomes one bounded typed JSON-RPC error
  (`code -32001`) without terminating later requests.
- [#50](https://github.com/teemuki8/libgdx-agent-runtime/issues/50) — application callback
  failures expose structured `ApplicationFailureEvidence` (stable category, exception class,
  session-prefixed correlation ID such as `sessionId|failure-N`, optional sanitized detail)
  instead of raw exception messages or stack traces. Sanitized detail is bounded at 1,024 code
  units, appears only in the structured field, and a throwing sanitizer fails closed with raw
  throwables routed to non-stdout local logging only.

### Protocol 2.0 and removed-entity history

- [#48](https://github.com/teemuki8/libgdx-agent-runtime/issues/48) — removed entities remain
  queryable while retained history exists. The additive
  `AgentRuntime.entityHistory(EntityId, FrameRange, long versionOffset, int versionLimit)` returns
  an immutable `EntityHistoryPage` with newest-frame `current`, the bounded final pre-removal
  `finalRetainedState` snapshot (never synthesized), independent version cursors, partial-eviction
  and retained-frame-bound metadata, and a distinct `ENTITY_HISTORY_NOT_RETAINED` failure once
  every retained frame holding the entity is evicted. The existing two-argument
  `entityHistory(EntityId, FrameRange)` and the `runtime_entity` command remain frozen.
  `ProtocolVersion.V2` is now `CURRENT`.

## Protocol compatibility and negotiation

Protocols 1.0-1.13 remain supported exact-version contracts in the 2.0.0 artifacts. Their frozen
golden fixtures remain byte-for-byte unchanged, and every V1.13 command, JSON/MCP schema, result
shape, error code, bound, and negotiation path remains available. Protocol 2.0 is additive:

- Clients select an exact protocol version in the `protocol` negotiation field, as before; 1.x
  requests receive their exact legacy shapes. As an intentional security hardening, callback-failure
  diagnostic values no longer expose raw application exception messages: they contain only the
  642-character `correlationId|category|exceptionClass` envelope and never sanitized or raw detail.
- Under version 2.0, `capability(version, command)` enables every existing V1.13 command despite
  its zero minor, plus the additive `runtime_entity_history` command and the
  `ENTITY_HISTORY_NOT_RETAINED` error category. Protocol 2.0 responses also carry the structured
  `ApplicationFailureEvidence` in callback-bearing command, checkpoint, input, and determinism
  failure results.
- Any other exact version returns `PROTOCOL_VERSION_UNSUPPORTED` before command execution, exactly
  as before.

The frozen 1.x wire contracts in already published 1.x artifacts are not altered by this release
(ADR 0011).

## Breaking Java changes and migration

The 2.0.0 Java API intentionally breaks source and binary compatibility in exactly two families:
structured failure evidence on callback-bearing public types, and diagnostic-limit minimum
capacities. Protocol schemas remain compatible; callback-failure diagnostic content changes as
described above.

### 1. `CaptureDiagnostic` carries structured failure evidence

`CaptureDiagnostic` replaces its `exceptionClass` and `message` components with one
`ApplicationFailureEvidence failure` component:

```java
// 1.x
CaptureDiagnostic d = new CaptureDiagnostic(provider, entityId, property, exceptionClass, message);
String cls = d.exceptionClass();
String msg = d.message();

// 2.0
CaptureDiagnostic d = new CaptureDiagnostic(provider, entityId, property, failure);
String cls = d.failure().exceptionClass();
String msg = d.failure().legacyEnvelope();
```

The protocol 1.x projection retains the old `exceptionClass` and `message` wire fields. Their
shape is unchanged, while the `message` value intentionally changes from a raw application
exception message to `failure.legacyEnvelope()`.

### 2. Callback-bearing evidence records gain `applicationFailure`

`CommandStatus`, `CheckpointOperation`, `InputInjection`, and `DeterminismResult` each gain an
`Optional<ApplicationFailureEvidence> applicationFailure` final component while retaining their
`diagnostic`/`message` fields. Record construction and deconstruction must add the component:

```java
// 1.x
CommandStatus s = new CommandStatus(requestId, state, submitted, deadline,
        started, completed, outcomeKnown, diagnostic);

// 2.0
CommandStatus s = new CommandStatus(requestId, state, submitted, deadline,
        started, completed, outcomeKnown, diagnostic, applicationFailure);
```

For callback failures the `diagnostic`/`message` field holds the 642-character legacy envelope and
`applicationFailure` carries the structured evidence; safe runtime-owned reasons (for example
execution-epoch-changed or evidence-evicted messages) keep their previous text with an empty
`applicationFailure`.

### 3. Diagnostic-text limits require a 642-character minimum

`RuntimeLimits.stringLength`, `CommandDispatchLimits.diagnosticLength`,
`CheckpointLimits.descriptionLength`, and `InputLimits.stringLength` now validate a 642 minimum so
the mandatory legacy envelope always fits; configurations below 642 are rejected at construction.
`CommandDispatchLimits.developmentDefaults()` and `CheckpointLimits.developmentDefaults()` raise
their diagnostic bounds from 512 to 1,024 so development defaults validate. `RuntimeLimits` and
`InputLimits` development defaults already exceed 642 and are unchanged.

### 4. Determinism callback-failure messages

Determinism callback-failure messages are the bare legacy envelope with no prefix; consumers that
parsed a prefix must read `DeterminismResult.applicationFailure()` instead.

The complete 2.0 compatibility note is in the [changelog](../../CHANGELOG.md).

## Upgrade steps

1. Update every runtime module you use to 2.0.0: `agent-runtime-core`, `agent-runtime-libgdx`,
   `agent-runtime-protocol`, `agent-runtime-mcp`.
2. Recompile: migrate `CaptureDiagnostic` construction/accessors and add the
   `applicationFailure` component to `CommandStatus`, `CheckpointOperation`, `InputInjection`, and
   `DeterminismResult` as shown above.
3. Review custom `RuntimeLimits`, `CommandDispatchLimits`, `CheckpointLimits`, or `InputLimits`
   instances: any diagnostic-text bound below 642 must be raised.
4. Select the protocol version your client implements. Existing 1.x clients keep their schemas and
   negotiation, but must treat callback-failure diagnostic values as the bounded legacy envelope
   rather than a raw application message. Adopt protocol 2.0 for `runtime_entity_history` or
   structured failure evidence.
5. No separate JVM can inspect a running game: MCP must remain in an application-owned same-JVM
   development launcher, unchanged from 1.0.0.

## Qualified platforms and dependencies

The release is compiled and tested with JDK 25 on Linux, Windows, and macOS. The real native
fixture qualifies LWJGL3 desktop on Linux under Xvfb; Android, iOS, and web are not release
claims. The reviewed direct dependency set is unchanged from 1.0.0: libGDX 1.14.2, Jackson 2.22.1,
Java MCP SDK 2.0.0, and JUnit 6.1.2.

## Release verification

The candidate is accepted only when the exact release head passes the full repository gate on the
isolated Linux Xvfb runner and CI on Linux, Windows, and macOS:

```bash
xvfb-run -a ./gradlew -PreleaseVersion=2.0.0 \
  clean check javadoc generatePomFileForMavenJavaPublication \
  --warning-mode=fail
```

The tag-driven staging workflow additionally signs and uploads the publication to the Sonatype
Portal OSSRH Staging API with the same `-PreleaseVersion=2.0.0` value derived from the `v2.0.0`
tag.
