# Issues #40–#50 and release 2.0.0 design

## Objective

Resolve every currently open repository issue (#40 through #50), merge each fix through a focused pull request, verify that no actionable repository issue remains open, and create release 2.0.0 — a narrowly scoped breaking release. The Java diagnostic model moves to structured immutable failure evidence with validated diagnostic-limit minimums, and new wire behavior uses protocol 2.0; protocol 1.0–1.13 wire contracts remain immutable and supported. The release boundary includes a GitHub tag and release plus Maven Central candidate staging. It explicitly excludes the irreversible Maven Central publish operation.

## Delivery structure

Each issue is implemented and reviewed in its own pull request. Every issue branch starts from the current remote `main` after the preceding dependency has merged. A pull request closes exactly its issue, contains its behavioral regression coverage, and updates only the contract, guide, Javadoc, or changelog text affected by that fix.

The execution order keeps shared safety behavior ahead of consumers:

1. #50 introduces structured immutable `ApplicationFailureEvidence` — independently bounded mandatory category, exception class, unique deterministic correlation ID, and optional application-owned bounded sanitized detail — removes raw application exception messages from externally queryable evidence, and validates diagnostic-limit minimum capacities sufficient for the documented mandatory legacy envelope; callback-bearing public evidence types may change in 2.0 to carry this record while protocol 1.x adapters keep emitting their exact old shapes with sanitized bounded legacy text.
2. #42 safely publishes monotonic lifecycle state across threads.
3. #41 releases every callback-bearing registry and pending control/input reference on close while retaining only documented immutable completed evidence.
4. #40 makes dynamic entity traversal capture-thread-confined, sequential, deterministic, and bounded at enumeration.
5. #45 enforces event, decision, and cause limits while an open frame is being populated.
6. #43 budgets canonical determinism evidence incrementally and stops at the first exceeded bound.
7. #46 makes checkpoint creation and replacement failure atomic.
8. #47 records throwing simulation conditions as `CALLBACK_FAILED` terminal evidence while preserving a sanitized typed command failure.
9. #48 keeps removed entities queryable while history is retained, adds bounded Java history-page/current-state APIs, and introduces protocol 2.0 for the new wire shape — entity-history pagination/current state plus structured failure evidence — while preserving protocols 1.0–1.13 unchanged.
10. #44 applies bounded strict-UTF-8 JSON-RPC line framing and protocol parser constraints before stdio request materialization.
11. #49 serializes the actual outgoing response through a hard byte limit so checked bytes and sent bytes are identical and no unbounded intermediate response is created.

If implementation evidence proves a strict dependency differs from this order, only the affected adjacent issues may be reordered. Issue boundaries remain separate.

## Behavioral and security invariants

The work preserves the module direction `runtime-mcp -> runtime-protocol -> runtime-core <- runtime-libgdx`. Core remains JDK-only and creates no thread, scheduler, listener, filesystem access, or reflection surface. Application callbacks execute only through existing capture-thread and application-dispatch contracts.

All externally visible values remain immutable, deterministic, deeply bounded, and stably ordered. Limits are enforced before expensive allocation or retention. Observed and truncated counters saturate without overflow. Protocol inputs and MCP schemas remain closed. In release 2.0.0, failures expose structured immutable `ApplicationFailureEvidence` with independently bounded category, exception-class, and correlation-ID fields plus optional sanitized detail; diagnostic limit records validate minimum capacities sufficient for their documented mandatory legacy envelope while every individual structured field keeps its own hard maximum. Raw application messages and stack traces never cross the protocol boundary; protocol 1.x adapters continue emitting their exact old wire shapes with sanitized bounded legacy diagnostic text.

Completed immutable history promised after close remains queryable. Mutable providers, callback registries, pending commands, scheduled input/control state, and opaque handles are released or disposed according to their ownership contracts.

## Per-issue implementation loop

For each issue:

1. Fetch and re-read the live issue and comments.
2. Trace the production path and nearest existing test conventions.
3. Add a focused behavioral regression test and observe the expected failure.
4. Implement the smallest source fix that satisfies every acceptance criterion.
5. Run the focused test, the owning-module verification gate, and any affected cross-module, fixture, schema, Javadoc, or Xvfb gate.
6. Update durable public documentation and the Unreleased changelog only when behavior visible to users changes.
7. Review the complete issue-only diff, commit, push, and open a ready pull request containing exact validation evidence and `Fixes #N`.
8. Review the actual remote pull request, address actionable findings, and wait for required checks on the exact reviewed head.
9. Merge only a clean, mergeable, current head with successful required checks; verify the issue closed and reconcile local `main` before starting the next issue.

No test, validator, warning policy, bound, or security boundary is weakened to make a gate pass.

## Verification strategy

Focused tests cover the issue’s observable success path and applicable lifecycle/thread misuse, hard bounds, truncation or eviction evidence, ordering, callback failure, and structured failure behavior. Cross-module public changes run the repository `check` gate. Native integration changes run the real LWJGL3 fixture under `xvfb-run` on Linux.

Before release, the exact release head runs `.agents/skills/libgdx-agent-runtime-dev/scripts/verify.sh full`, including clean checks, published-module Javadocs, packaging, and the Xvfb-backed fixture. Pull-request and release workflow checks must succeed on the exact SHA being tagged.

## Release 2.0.0

After issues #40–#50 merge, fetch the live open-issue list again. Any newly opened actionable issue in this repository is resolved through the same issue-only workflow before release; umbrella or externally blocked items must have an explicit, evidence-backed disposition rather than being silently ignored.

Prepare a dedicated release pull request from current `main` that:

- updates the development default from `1.0.1-SNAPSHOT` to `2.0.1-SNAPSHOT`; the release workflow derives the immutable published artifact version from the tag and passes `-PreleaseVersion=2.0.0`;
- moves all accumulated Unreleased entries into a dated `2.0.0` changelog section;
- adds `docs/releases/2.0.0.md` with issue impact, protocol 2.0 compatibility, upgrade notes documenting every intentional 2.0 incompatibility and its migration path, and exact verification;
- compares generated public/protected Javadocs and documented behavior with 1.0.0 under ADR 0011, listing every intentional 2.0 incompatibility;
- updates any release metadata required by the existing workflows without altering publication credentials or trust boundaries.

After the release pull request is reviewed, green on its exact head, and merged, create and push tag `v2.0.0`, then create the GitHub release for that tag. Confirm the tag and release target the reviewed merge commit. Approve the existing `Stage Maven Central` environment deployment, verify that the staged candidate contains exactly the four expected coordinates at version `2.0.0` and reports successful validation, and record its deployment identifier. Do not invoke the Maven Central publish endpoint; final immutable publication requires a separate explicit authorization.

## Completion evidence

Completion requires all of the following current-state evidence:

- no unresolved actionable open repository issue remains;
- issues #40–#50 are closed by merged focused pull requests;
- all issue acceptance criteria are covered by tests or direct scenario evidence;
- the release head passes the full repository Xvfb gate and exact-head GitHub checks;
- tag `v2.0.0` and the GitHub release target the reviewed release commit;
- the Maven Central candidate is staged and validated for the exact four coordinates;
- the irreversible Maven Central publish operation has not been invoked;
- local `main` is reconciled with remote `main`, with any intentional divergence reported.
