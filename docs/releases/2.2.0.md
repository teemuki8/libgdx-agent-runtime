# 2.2.0

Release 2.2.0 adds bounded deterministic replay execution and exact-tick input timeline execution
on top of the 2.1 simulation evidence. It is an additive minor release: existing Java integrations
and exact protocol 1.0-1.13 and 2.0-2.4 clients remain supported, while the new execution
capabilities use protocols 2.5-2.6.

The application remains authoritative for its main loop, input scheduling, mutation, rendering,
Box2D world and listener lifecycle, scenario reset, native-object replacement, and disposal. The
runtime creates no hidden thread, timer, renderer, physics loop, or object traversal. Replay and
input timelines never roll back, re-execute, or mutate application state without explicit
acknowledged fixed-step control.

## Published artifacts

All artifacts require Java 25 and use group `io.github.teemuki8`:

- `agent-runtime-core`
- `agent-runtime-libgdx`
- `agent-runtime-box2d`
- `agent-runtime-protocol`
- `agent-runtime-mcp`

`runtime-fixtures` and `runtime-examples` are repository qualification and consumer-guidance code;
they are not published.

## Highlights

### Bounded replay execution

Protocol 2.5 adds replay-ready recording capture and execution. Recordings are started explicitly
through `ReplayRegistry` from exactly one application-owned scenario or opaque checkpoint origin,
and carry baseline facts plus bounded registered-input evidence. Execution pauses first, chooses
one origin, selects observable evidence, then injects registered inputs in stable tick order and
advances contiguous fixed ticks through acknowledged fixed-step control.

Selected immutable baseline/tick evidence reports `EQUAL`, the first `DIVERGED` tick with both
run/frame correlations and values, or safe `INCONCLUSIVE` under explicit input, tick, evidence,
retention, and deadline limits. Failed transitions are never re-executed; terminal result
reservation is a strict upper bound; sanitized application failures keep replay incomplete.
Recording schema 1 is unchanged, so recordings captured by 2.1 remain consumable. Closed local
stdio MCP tools (`runtime_replay_*`), a compiled workflow transcript, and real Box2D/LWJGL3
fixtures qualify the additive contract. Replay never proves equality over incomplete evidence and
never claims causality.

### Deterministic input timelines

Protocol 2.6 adds one bounded, application-dispatched operation that validates and executes an
ordered sequence of explicit registered input transitions through exact acknowledged fixed ticks.
Transitions sharing a local tick execute in request-list order; ticks without transitions still
advance; persistent held controls remain application-owned.

Execution is fail-stop with hard input/tick/evidence/retention/deadline limits, explicit
`completed` / `failed` / `not-executed` transition testimony, no rollback or automatic retry, and
never a false `COMPLETED`. Timeline evidence consumes the normal registered-input and
controlled-tick evidence; failed, redacted, timed-out, or lifecycle-invalidated evidence keeps
replay inconclusive. Closed protocol 2.6 JSON, the `runtime_input_timeline` MCP tool with
registered-input-specific scalar variants, a compiled workflow recipe, a tested MCP transcript
step, and actual-native Box2D/LWJGL3 fixture coverage qualify the additive contract. Input
timelines are rejected for v1 protocol clients.

## Protocol compatibility

Protocols 1.0-1.13 and 2.0-2.4 keep their exact supported command and response shapes. Release
2.2.0 adds:

- Protocol 2.5: `runtime_replay` recording capture and execution commands with
  `EQUAL`/`DIVERGED`/`INCONCLUSIVE` results.
- Protocol 2.6: `runtime_input_timeline` exact-tick input transition execution.

`ProtocolVersion.CURRENT` is 2.6. Unsupported exact versions and commands fail before execution.
Replay and input timelines reuse ordinary entity, history, event, and controlled-tick schemas;
Box2D types do not enter `runtime-core`, protocol commands, or MCP transport values.

## Upgrade and adoption

Existing 2.0.0 and 2.1.0 consumers can update their current runtime modules to 2.2.0 without
adopting the new execution APIs. Consumers adopting replay or input timelines should:

1. Align every runtime artifact on version 2.2.0.
2. Register the fixed step before `runtime.start()` and return the delta actually executed.
3. Start replay recordings explicitly from one scenario or opaque checkpoint origin.
4. Use protocol 2.5-2.6 only for the corresponding additive commands.
5. Treat truncation, eviction, failed transitions, deadlines, and `INCONCLUSIVE`/non-completed
   results as incomplete evidence, never as proof of equality or success.

See the [agent cookbook](../guides/agent-cookbook.md) for executable integration recipes covering
the replay and input-timeline workflows.

## Qualified platforms and dependencies

The release is compiled and tested with JDK 25 on Linux, Windows, and macOS. Actual-native LWJGL3
and Box2D conformance is qualified on Linux under Xvfb. Android, iOS, web, and cross-platform
Box2D bitwise equality are not release claims.

The reviewed direct dependencies remain libGDX 1.14.2, Jackson 2.22.1, Java MCP SDK 2.0.0, and
JUnit 6.1.2. `runtime-core` remains JDK-only and resolves only `java.base` under `jdeps`.

## Staging boundary

The reviewed tag and GitHub release are separate from signing, Central staging, inspection, and
immutable publication. Publishing the GitHub release may start the protected `Stage Maven Central`
workflow, but the environment approval remains a distinct maintainer action.
Maven Central publication requires separate authorization. Publishing also requires current terms
acceptance, a validated candidate, and inspection of the exact five coordinates. This release note
does not claim that version 2.2.0 has been staged or published to Maven Central.
